# ADR-032: Structural Audit Gate (Task 38.5)

**Status:** Accepted

## Context
Tasks 1–38 each produced a foundational component or framework — trading-domain frameworks, infrastructure frameworks like Exchange Adapters, and eventually the composition root itself. Task 38 specifically declares and wires **24** of those completed frameworks (`app/wiring.py:COMPONENT_REGISTRARS`) into a disposable dry-run container that proves the declared DI graph for those 24 wires. 38 tasks and 24 wired frameworks are not the same count, and this ADR does not conflate them: several Tasks 1–38 produced infrastructure (`core/`, `config/`, `events/`, `trading/`) or a framework not among the 24 wired ones (`exchange_adapters/`, Task 17 — see H-2 below), not one of the 24 `COMPONENT_REGISTRARS` entries. No task to date had re-examined the system *as a whole*, from real committed source rather than prior claims, for structural cracks that only become visible once every framework is considered together — cross-framework coupling no single framework's own review would catch, a safety boundary asserted in one task's docstring but never checked against a sibling's real behavior, or a trading-safety control the roadmap assumes exists but that no task actually built. `docs/prompts/task-38.5.md` specified a code-read-only audit to close that gap and, critically, to establish a gate: Task 39 should not begin work on top of an unverified foundation.

## Decision
Adopt a standing rule: **any open Critical-severity finding from a Task 38.5-class structural audit blocks the next dependent task from starting**, until each such finding is either resolved by a dedicated follow-up task or explicitly re-classified with a recorded justification. This gate is independent of what any particular audit run finds — it was decided as an architectural policy in `docs/prompts/task-38.5.md` before the audit ran, and this ADR records that policy as accepted regardless of outcome.

**Amendment, this closeout pass:** the policy above was written assuming the audit could conclusively determine whether a Critical finding exists. Five successive passes (v1–v5) of this audit each found something the previous pass's method could not see, which is itself evidence the trace has not converged on exhaustive. The policy is therefore amended to make explicit what it already implied: **if the audit cannot conclusively establish the absence of a Critical-severity path — as opposed to having discovered zero within what it walked — the gate is HOLD, not ALLOWED**, until either the assurance gap is closed by a stronger method or a deliberate, recorded decision accepts the residual risk. This is a distinct disposition from BLOCKED (which means a Critical finding *was* discovered); HOLD means the question was not conclusively answered either way.

**Task 38.8 Phase 0 — architecture and safety-boundary decision, 2026-08-24.** Per `docs/prompts/task-38.8.md` §5/§9, Option **D** (a justified hybrid) is selected, scoped to exactly **2 of the 11** protocol families §2 names: **context managers** (`__enter__`/`__exit__`, including async equivalents) and **property/descriptor access** (`__get__`/`__set__`/`__delete__`). The remaining **exactly 9** families are unsupported under this decision, each reported in `unsupported_protocol_families` and each requiring its own later, separately authorized Phase 0 analysis before it may be added to this scope: **(1)** iteration/comprehensions, **(2)** unpacking, **(3)** await/async iteration, **(4)** equality/ordering/arithmetic operators including reflected forms, **(5)** truth testing, **(6)** membership, **(7)** subscription/assignment/deletion, **(8)** hashing, **(9)** formatting including `__str__`/`__repr__` fallback. (Full, unselected Option A would mechanize all **11**; this decision selects neither Option A's 11 nor Option C's 0, but Option D's named 2.)

**Syntax sites vs. dispatch events (context managers).** One `ast.With`/`ast.AsyncWith` item is one syntax site and produces **two** protocol-dispatch events — `__enter__` and `__exit__` — each identified by `(module, qualname, line, column, family, protocol_method)`. No context-manager syntax site is ever claimed to have one target; `syntax_sites_total` and `dispatch_candidates_total` are reported as two distinct figures, reconciled only via `dispatch_candidates_total == resolved_dispatches + unresolved_dispatches`, with `explicit_path_duplicates` as a subset annotation, never an addend.

**Syntax sites vs. dispatch events (descriptors), and the full attribute-residual set.** One `ast.Attribute` node is one syntax site; its AST context determines the operation implicated — `Load`→`__get__`, `Store`→`__set__`, `Del`→`__delete__` — so each site contributes at most one dispatch candidate for the context-appropriate operation. An unresolved receiver emits one `unresolved` candidate for that operation; a resolved receiver whose attribute is an ordinary, non-descriptor attribute contributes a `resolved_non_descriptor_exclusion`, counted separately and excluded from the `resolved_dispatches`/`unresolved_dispatches` partition entirely. **This exclusion proves only that no descriptor dispatch occurs for the context-appropriate operation at that site — it does not claim, and must never be read as claiming, that no implicit execution occurs there at all.** A class overriding the base attribute-access machinery remains a named, unsupported residual across all four relevant contexts: **`Load`** may invoke a custom `__getattribute__` or `__getattr__`; **`Store`** may invoke a custom `__setattr__`; **`Del`** may invoke a custom `__delattr__`. All four names are recorded as unsupported residual.

**Terminology — false negatives vs. observed uncertainty.** A descriptor or context-manager site the mechanism enumerates is reported as one of two distinct kinds of observed uncertainty, never a false negative, when it cannot be classified resolved-safe or resolved-forbidden: **(a)** the receiver cannot be resolved to a concrete type at all; or **(b)** the receiver *is* resolved and a concrete dunder target *is* found, but that target is C-implemented or otherwise source-unavailable-by-construction and is classified `unresolved` under the walker's existing source-availability rule. A **false negative** is reserved exclusively for a site or path the mechanism never enumerates at all.

**Ten-criteria evaluation, with concrete reasoning recorded here:**
1. **Soundness** — a resolution is accepted only when the receiver's static type and the context-appropriate dunder target are both soundly established by the walker's existing identity-first discipline (`_resolve_target`/`classify_callable`). AST syntax (the `ast.With`/`ast.AsyncWith`/`ast.Attribute` shape and its context) **selects which protocol-method candidate is under consideration at a site — it identifies the candidate, never verifies it.** Only the resolved, live callable identity that candidate actually points to receives a classification verdict. AST shape is never asserted to play no role in soundness — it is exactly what makes a site a candidate in the first place; its role is bounded to candidate-selection, never substituted for the identity-based verdict itself.
2. **Polymorphism/duck typing** — an unresolvable receiver (case (a) above) produces an explicit `unresolved` dispatch record, never a default-safe verdict; a `Protocol`-typed or untyped-parameter receiver is treated identically to any other unresolvable receiver under the walker's existing type-inference limits.
3. **False negatives, precisely qualified** — confined, within the scope this decision actually walks, to genuinely **accepted** `StaticWalker.walk()` states (post visit-key dedup, post budget, post source-availability) and to the **two selected AST shapes**. This is not a claim of complete or exhaustive coverage beyond that narrow scope: an unreachable-source/graph-reachability gap (a callable the walker never visits at all, `docs/prompts/task-38.8.md` §1's third category — unchanged, out of this decision's scope), a receiver whose declared type diverges from its actual runtime type (criterion 4), and any instance of the **9 unsupported families** all remain real, named residual risks this decision does not close and must never be described as covered.
4. **False positives/manufactured confidence** — bounded by the same declared-vs-runtime-type risk the walker's existing parameter-annotation substitution already carries; this decision introduces **no new category of inference risk, but the existing risk is extended to the newly enumerated context-manager and descriptor sites.**
5. **Deterministic termination** — any recursion into a resolved `__enter__`/`__exit__`/`__get__`/`__set__`/`__delete__` target is gated by the walker's existing `(callable identity, specialization)` visited-state dedup and existing `max_total_walk_steps` budget; no separate recursion or budget mechanism is introduced.
6. **Specialization-state growth** — not estimated here. Phase B's real re-run against the committed Phase A.1 mechanism is what measures this.
7. **CPython-version coupling** — materially lower and more stable than the rejected bytecode-based Option B, but not zero: the AST shapes this decision inspects are stable across recent CPython minor versions but are not immune to language-level change, and this decision's soundness is bounded specifically by this repository's `==3.12.*` pin (`pyproject.toml:6`), never asserted as version-independent.
8. **Maintenance burden** — bounded to two families' worth of new AST-shape handling in `audit_harness/`, structurally smaller in scope than mechanizing the full 11 under Option A (a scope comparison, not a magnitude estimate).
9. **Implementation size** — not estimated here. Phase A.1's committed implementation is what establishes this.
10. **Fail-closed gate compatibility** — the additive schema fields this decision requires (`docs/prompts/task-38.8.md` §8), and any new `all_clear`-contributing term they introduce into `audit_harness/report.py`, **are themselves new plumbing** — never assumed safe merely by routing toward existing machinery. Missing implicit-dispatch evidence (fields absent or unpopulated), malformed evidence (a schema violation), work-budget exhaustion during context-manager/descriptor resolution, and any unresolved implicit-dispatch record of either kind (a) or (b) above must each independently keep `ADR-032` at HOLD — none may be defaulted, ignored, or treated as passing, and the new `all_clear` term (if one is introduced) must be proven, by a dedicated regression test, to require all four clear before Phase A.1's mechanism may be trusted.

**The 9 deferred families, stated precisely:** `await`/async iteration requires its own future Phase 0 analysis of `__await__`'s **multi-stage iterator execution** (a coroutine's `__await__` yields across a generator-based state machine, not a single call-and-return); subscription requires its own analysis of **instance/class/metaclass dispatch distinctions** (`obj[k]` vs. class-level `SomeGeneric[T]` via `__class_getitem__` vs. a metaclass's own `__getitem__` are three different dispatch paths); hashing requires its own analysis of `__hash__`, which **may be triggered by set/dict-key insertion — insertion is the direct triggering mechanism, not a fallback**; formatting (`__format__`, with its own documented `__str__`/`__repr__` fallback) **remains explicitly unsupported**, with no partial coverage claimed. None of the 9 is a straightforward follow-on addition to this scope; each requires its own future, separately authorized Phase 0 record before any implementation work on it begins.

This update changes no Layer 1 counter beyond what Phase A.1/B's own broadened `explicit_calls` accounting already reflects, does not close H-1 or H-2, does not authorize or reject `builtins.str.join`'s separately pending Phase 0 review (still paused and unrecorded), and does not modify `EXACT_IDENTITY_POLICY`. A future, separately scoped and authorized task would be required to drive `implicit_dispatch.unresolved_dispatches` toward zero within the 2 mechanized families, or to run this task's own Phase 0 process again for any of the 9 remaining families — neither is undertaken by this Phase C update.

## Alternatives Considered
- **No formal gate — treat the audit as informational only.** Rejected: an audit whose findings carry no consequence is easy to produce and easy to ignore; the entire point of running a structural audit before Task 39 is to make its outcome actionable.
- **Gate on any open finding, regardless of severity.** Rejected: with 9 Low findings already on record (mostly `baseline: unknown` typing gaps and test-coverage notes), gating on every open item would block indefinitely on cosmetic issues unrelated to safety. The severity rubric exists precisely so the gate tracks what actually matters — a real reachable I/O/trading/inference/credential-leak path.
- **Gate on High findings too.** Rejected for this run, but not dismissed as a future policy: the two High findings here are about the accuracy of an architectural *claim*, not about an unsafe path existing. Blocking Task 39 on a documentation-accuracy issue would be disproportionate; the risk register's disposition (`Open`) already ensures they aren't forgotten.
- **Re-run the audit until 0 High findings too, before allowing Task 39.** Rejected: this would make audit accuracy — finding real, pre-existing issues — a reason not to ship the audit, incentivizing under-reporting. The gate is about newly-tolerable risk (Critical), not about the audit finding nothing.
- **Treat "0 Critical findings discovered" as equivalent to "0 Critical findings exist" and leave the gate ALLOWED.** Rejected in this closeout pass: five successive passes each found a real gap the last one's method missed, which is direct evidence against treating the current pass as the last word. Conflating "discovered none" with "none exist" would make the gate's own Critical-only criterion unfalsifiable — it would always read ALLOWED regardless of how much of the codebase the method actually covered, which defeats the purpose of having a gate at all.
- **Re-run yet another ad hoc `/tmp` script (a "v6") to try to close the gap immediately.** Rejected for this pass, per its own explicit instruction: the v1–v5 pattern of one-off scripts each fixing the previous one's blind spot is itself part of the problem M-7 names — another one-off script would likely find one more gap and leave the same open-ended uncertainty, not close it. The gap needs a source-controlled, reusable harness (Task 38.6), not another iteration of the same throwaway-script method.

## Consequences
### Positive
- Task 39's eventual start (once the gate is re-evaluated) will rest on a documented, evidence-based, independently-derived, and honestly-scoped confirmation of Task 38's dry-run boundary, rather than an assumption carried forward from Task 38's own completion report or from an overclaimed "complete" audit.

- The Task 38.6 harness turns M-7's four named methodological gaps from prose descriptions into passing, re-runnable tests (`tests/audit_harness/`) — the next commit that touches any of these areas gets checked automatically, not re-derived by hand in a sixth pass.

- The two High findings remain unresolved; a future task must still decide whether to correct the documentation claim, migrate the older frameworks toward DI-only isolation, or accept the difference as intentional and document it as such.
- The seven Medium trading-safety/I-O/assurance gaps and the new Low (L-10) remain unimplemented by design (this audit explicitly forbids implementing anything it finds missing) — whatever eventually follows must not assume they've been silently closed.
- `exchange_adapters`' exclusion from the composition root (H-2) means it continues to be un-covered by the 24/24 preflight check until a follow-up task adds it — independently re-confirmed by the Task 38.6 harness's own discovery step.
